# 02 Win32 とゲームループ

DirectX は「ウィンドウの中に絵を描く仕組み」なので、まずウィンドウが要る。
そして、ゲームは「止まらずに回り続けるループ」の中で動く。この 2 つが土台の土台。

## この章でできるようになること

- ウィザードを使わず、1 つの `.cpp` でウィンドウを出せる
- メッセージループとウィンドウプロシージャの役割を言える
- 固定ステップ（1/60 秒ずつ進める）の時計を自分で書ける

## 読むときの問い

### ウィンドウとメッセージ

1. Windows のプログラムは、キー入力・マウス・「閉じる」ボタンをどうやって知るか。`WndProc` は誰が呼ぶか
2. `_tWinMain` のループは `GetMessage` ではなく `PeekMessage` を使っている。違いは何か。ゲームが `PeekMessage` を使う理由は
3. ループの中で、`PeekMessage` を `while` で回して**溜まっている物を全部**さばいてから `wc.update()` している。1 フレームに 1 件だけさばく書き方だと何が起きるか（コメントに書いてある）
4. `WndProc` の `WM_CLOSE` と `WM_DESTROY` は、それぞれいつ来るか。ループを抜ける `WM_QUIT` は誰が出すか
5. `timeBeginPeriod( 1 )` は何のためか（`Framework.cpp` の `preUpdate` の `Threading::sleep( 1 )` と関係がある）

<details><summary>答え</summary>

1. Windows が「メッセージ」としてプログラムの待ち行列に入れる。プログラムは `PeekMessage`（か `GetMessage`）で取り出し、`DispatchMessage` で Windows に渡し返す。すると Windows が、そのウィンドウに登録された `WndProc` を呼ぶ。`WndProc` を自分で直接呼ぶことは無い
2. `GetMessage` はメッセージが来るまで止まって待つ。`PeekMessage` は無ければすぐ戻る。ゲームは入力が無くても毎フレーム動かないといけないので、待たない `PeekMessage` を使う
3. キーを押し続けたときの自動リピートやマウスの移動で、メッセージは 1 フレームに何件も来る。1 件ずつだと溜まり続け、後から押したキーの反映が大きく遅れる
4. `WM_CLOSE` は「閉じる」ボタンや Alt+F4 で来る（まだ閉じていない。ここで終了の確認などができる）。`WM_DESTROY` はウィンドウが壊されるときに来る。`WM_QUIT` は `WM_DESTROY` の中で `PostQuitMessage` を呼ぶと出る
5. Windows の `Sleep` の細かさは既定で約 15.6 ミリ秒。`Sleep( 1 )` のつもりが 15 ミリ秒寝ることがある。`timeBeginPeriod( 1 )` で 1 ミリ秒まで細かくする。フレームレートを合わせるための待ちが粗くならないようにしている

</details>

### 1 フレームの前後

`Framework.cpp` の `WindowCreator::update`・`preUpdate`・`postUpdate` を読む。

1. 最小化している間は何をしているか。なぜ描かないのか
2. `preUpdate` の `while ( ( currentTime - mPreviousFrameTime ) < mIdealFrameInterval )` は何をしているか
3. `beginDraw` と `endDraw` の間に、ゲーム側のコードが全部入る。この形（始め・終わりを土台が持ち、間だけをゲームが書く）の良い所は

<details><summary>答え</summary>

1. 50 ミリ秒ずつ寝る。見えないウィンドウに描いても無駄で、最小化中は描く先の大きさが 0 になることもあるため
2. 前のフレームから決めた間隔が経つまで、1 ミリ秒ずつ寝て待つ。フレームレートの上限を付けている（`setFrameRate` で決める。呼んでいなければ間隔 0 で待たない）
3. ゲーム側は「画面を消す」「Present する」を忘れようが無い。入力の更新・計測・デバッグ表示のような「毎フレーム必ず要る物」も 1 か所に集まる

</details>

### 固定ステップ

`SceneManager::update` と `FixedStepClock::ticksToRun` を読む。

1. モニターが 144Hz（1 秒に 144 回描く）のとき、1 回の描画でシーンの `update` は何回呼ばれるか。30fps まで落ちたときは
2. `mAccumulated` には何が貯まっているか。`ticksToRun` の最後で `ticks * kTickSeconds` を引くのはなぜか（0 に戻さないのはなぜか）
3. `kMaxTicksPerFrame`（5）を超えたとき、貯まった時間を捨てている。捨てないと何が起きるか
4. 一時停止（`setPaused`）のとき `mAccumulated = 0.0` にしているのはなぜか
5. 「毎フレーム、前のフレームからの経過時間（デルタタイム）を掛けて動かす」やり方と比べて、固定ステップの良い所・悪い所は
6. 入力（`Pad::instance()->update()`）は、`update` を回すループの**前**に 1 回だけ読んでいる。ループの中で毎回読まないのはなぜか
7. `mAccumulated` が `float` ではなく `double` なのはなぜか

<details><summary>答え</summary>

1. 144Hz：1 描画は約 6.9 ミリ秒で、1 ティック（16.7 ミリ秒）に足りない。貯めていき、足りた回だけ 1 回呼ぶ。ならすと 144 回の描画のうち 60 回で、0 回の描画と 1 回の描画が混ざる。30fps：1 描画は約 33 ミリ秒なので、毎回 2 回
2. まだゲームの時間に使っていない実時間。使った分だけ引き、端数は次へ持ち越す。0 に戻すと端数が毎回捨てられ、ゲームが実時間より遅く進む
3. 重いフレーム → 貯まる → 次のフレームで update が増える → さらに重くなる → さらに貯まる、と遅れが膨らみ続けて止まる（「死のらせん」）。上限で切り、ゲームの方を少し遅くして逃がす
4. 止めていた間の時間を、戻した瞬間にまとめて進めてしまわないように
5. 良い所：1 回の更新で進む量がいつも同じなので、当たり判定や物理が「速い PC と遅い PC で結果が違う」にならない。同じ入力なら同じ結果になる。悪い所：描画と更新の回数がずれるので、何もしないと動きが少しカクつく（描画のたびに「前の状態と今の状態の間」を補間すれば消せる。このゲームは補間していない）
6. `Pad` は「このフレームで押された瞬間か」を持っている。ループの中で読むと、update が 2 回の描画では 2 回目に「押した瞬間」が消え、0 回の描画では押したこと自体を落とす。描画 1 回につき 1 回読むことで、update の回数に左右されなくなる
7. 小さな数を何時間も足し続けるので、float だと誤差が積もる

</details>

### 課題 02-2：固定ステップの時計

M0 のループに、自分で書いた時計を入れる。

- `std::chrono::steady_clock` で経過時間を測る
- 1/60 秒ぶん貯まるたびに `update()` を呼ぶ（中身はカウンタを 1 足すだけでよい）
- 毎フレーム `draw()` を 1 回呼ぶ（カウンタを 1 足す）
- 1 秒ごとに、ウィンドウのタイトルに「update の回数／秒・draw の回数／秒」を出す（`SetWindowTextW`）
- 確かめ方：update は必ず 60 前後。draw はループの速さ次第。`draw()` の中で `Sleep( 50 )` して、update が 60 のままであること（1 回の draw で複数回 update されること）を見る。`Sleep( 500 )` にして、上限が無いとどうなるか・上限を付けるとどうなるかを見る

書けたら [FixedStepClock.cpp](../GameSrc/src/Core/FixedStepClock.cpp) と見比べる。

### 課題 02-3：補間（発展）

課題 02-2 に「左から右へ動く点」を足す（まだ描けないので、位置の数字をタイトルに出すだけでよい。M2 の後で絵にする）。
update で位置を進め、draw では `前の位置 + ( 今の位置 − 前の位置 ) × ( 貯まっている時間 ÷ 1 ティック )` を出す。
「Fix Your Timestep!」の最後の節がこれ。自分のゲームに入れるなら、どのクラスに何を足すことになるかを考える（入れなくてよい。考えるだけ）。
