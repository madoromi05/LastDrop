# このゲームで DirectX11 と C++ を学び直す

AI に書かせたこのゲーム（GameLib ＋ GameSrc。GameSrc だけで約 620 ファイル・約 4 万行）を、
**自分で書けて、言葉で説明できる物**にするための教材。

新しい入門書を 1 冊読むのではなく、「今ここにある自分のゲームのコード」を教科書にする。
作った物の説明（何を・なぜ）は `SummaryPlan/技術まとめ_ポートフォリオ.md` に既にあるので、ここには書かない。
ここに書くのは「**どの順に学ぶか・どこを読むか・何を自分の手で書くか**」。

## 考え方：読むだけでは書けるようにならない

どの章も同じ 4 段でできている。

| 段 | やること | ねらい |
|---|---|---|
| ① 先に読む | 公式ドキュメント・記事・本で考え方を知る | 言葉と全体像を知る |
| ② 自分のコードを読む | 「読むときの問い」に答えながら、対応するファイルを読む | AI が書いた所を自分の物にする |
| ③ 手で書く | 別プロジェクトの「ミニレンダラ」に、同じ機能をゼロから書く | 書ける力を付ける |
| ④ 説明する | 「説明できるか」に、コードを見ずに答える | 面接・ブログで話せるようにする |

②だけ・①だけで終えないこと。分かったつもりと書けるの間が一番遠い。

## 3 つの約束

1. **課題のコードは AI に書かせない。**
   AI に聞いてよいのは「このエラーは何と言っているか」「この API は何をする物か」「自分の説明は合っているか」まで。答えのコードは頼まない
2. **写すときも貼り付けない。**
   自分のゲームのコードを横に開いてよい。ただし手で打ち、1 行ごとに「この行が無いとどうなるか」を言えるか確かめる
3. **「説明できるか」に答えられるまで次の章へ行かない。**
   答えはノート（紙でもファイルでも）に自分の言葉で書く。そのままブログの記事と面接の答えの下書きになる

### 進める順

**基礎に自信が無ければ、章より先に問題集から始める。**

1. [問題集 01](問題集_01_Cpp基礎.md)（C++）を解く。4 択で 30 問取れるまで、入門の資料と行き来する
2. [問題集 02](問題集_02_DirectX11基礎.md)（DirectX11）を 1 回解く。最初は半分も取れなくてよい。「何を知らないか」を知るために解く
3. 章を進め、ミニレンダラの M2（三角形）と M5（テクスチャ）の後に、問題集 02 をもう一度解く。2 回目で満点が目標

問題集や章で知らない言葉に出会ったら、[用語集](用語集.md) を `Ctrl + F` で引く。

章は、00 → 01（途中まででよい）→ 02 → 03 → 04 → 05 → 06 → 08 → 09 → 07 → 10 の順を勧める。

- 01 の C++ は、先に全部やろうとすると止まる。1〜4 節だけやって先へ進み、分からない書き方に出会ったら戻る
- 07（スキニング）は行列に慣れてからの方が楽なので、08・09 の後でもよい
- 03〜06 が土台。ここを自分の手で書けるようになれば、08 以降は「同じ部品の組み合わせ」だと分かる

## コードの場所の書き方

行番号は書いていない。コードは今も変わっていて、すぐにずれるため。
**ファイル名と関数名（や変数名）**で書いてある。Visual Studio では、

- `Ctrl + T`：名前で探す（関数・クラス・ファイル）
- `Ctrl + Shift + F`：全部のファイルから文字で探す
- `F12`：定義へ飛ぶ ／ `Shift + F12`：使っている所を全部出す

## 使う道具

| 道具 | 何に使うか |
|---|---|
| Debug ビルドの出力ウィンドウ | Debug では D3D11 のデバッグレイヤーが付く（`ManagerImpl.h` の `D3D11_CREATE_DEVICE_DEBUG`）。間違った使い方をすると `D3D11 ERROR:` や `D3D11 WARNING:` が出る。**絵が出ないときは、まずここを読む** |
| F6 のエディタ | Render タブで G-Buffer の中身（色・法線・粗さ・深度・影のマップなど）を表示できる。08・09 章で使う |
| [RenderDoc](https://renderdoc.org/) | 1 フレームの描画を 1 回ずつ止めて見られる。どのドローコールで何が描かれたか・その時のステート・テクスチャの中身が分かる |
| Visual Studio のグラフィックス診断 | RenderDoc と同じことが VS の中でできる（Alt + F5） |
| git | 「消して書き直す」課題の答え合わせ（下） |

### 「消して書き直す」のやり方

ゲームの中の小さな関数を、自分で書き直す課題がある。やり方は毎回同じ。

1. 学習用のブランチを切る（例：`study/ch04`）。元のブランチは汚さない
2. 課題の関数の**中身だけ**を消す（宣言とコメントは残す）
3. コメントと呼び出し側を読んで、自分で書く。ビルドして動かす
4. `git diff` で元のコードと見比べる。違った所に「なぜ元はそう書いていたか」を書き足す
5. ブランチは捨ててよい（残すのはノートだけ）

## この教材が就活とブログにつながる所

- 各章の「説明できるか」は、`SummaryPlan/技術まとめ_ポートフォリオ.md` の 6 章（面接で聞かれそうな質問）と同じ向きの問い。ここで書いた答えを、技術まとめに書き足していく
- ミニレンダラは「AI を使わずに自分で書いた」と言い切れる物になる。面接で「AI に書かせた所と自分で書いた所」を聞かれたときの、正直な答えの材料になる
- 章ごとに 1 本、ブログの記事にできる（例：「定数バッファの並びを C++ と HLSL で合わせる」「全画面を三角形 1 枚で描く理由」）。ネタを比べるときは `C:\AIResorce\GameDev\記事ネタ評価軸.md` の軸で

## GameLib の出どころについて（推測）

`GameLib` のクラスの名前（`Framework`・`WindowCreator`・`PseudoXml`・`Tank`・`STRONG_ASSERT`・`HALT` など）は、
平山尚『ゲームプログラマになる前に覚えておきたい技術』（秀和システム）の付属ライブラリと同じ。
元は DirectX9 で、それを DirectX11 に載せ替えた物に見える（`ManagerImpl.h` に `match DX9` というコメントが残っている）。
これは名前からの推測なので、自分の記憶で確かめること。当たっていれば、この本が GameLib の土台の一番の教科書になる。
