# 05 テクスチャ・ステート・色空間

三角形に絵を貼り、重なりと透け方を決める。
この章の物（サンプラ・ブレンド・深度・ラスタライザ）は「ステート」と呼ばれ、どれも「作っておいて、描く前に付ける」という同じ形をしている。

## この章でできるようになること

- テクスチャを作り、シェーダから読める
- 4 種類のステート（サンプラ・ブレンド・深度ステンシル・ラスタライザ）が何を決めるか言える
- 半透明の物を描く順番の決まりを説明できる
- sRGB とリニアの違いと、どこで変換が起きるかを説明できる

## 言葉の整理

| ステート | 決めること | 付ける API | GameLib の関数 |
|---|---|---|---|
| サンプラ | テクスチャの読み方。画素の間をどう補うか（点・線形・異方性）、0〜1 の外をどうするか（繰り返す・端で止める） | `PSSetSamplers` | `setTextureFilter` |
| ブレンド | 描く色と、既にある色をどう混ぜるか | `OMSetBlendState` | `setBlendMode` |
| 深度ステンシル | 深度で比べるか・深度を書くか | `OMSetDepthStencilState` | `enableDepthTest`・`enableDepthWrite` |
| ラスタライザ | 裏面を捨てるか・塗るか線か | `RSSetState` | `setCullMode` |

GameLib は、使う組み合わせを起動時に全部作っておき（`ManagerImpl` のコンストラクタ）、描く前に番号で選んで付けている。
ステートは描画のたびに作る物ではない（作るのは重い。付けるのは軽い）。

### ブレンドの式

```
出る色 = 描く色 × SrcBlend  （BlendOp）  既にある色 × DestBlend
```

| GameLib の名前 | SrcBlend | DestBlend | 式 | 使い道 |
|---|---|---|---|---|
| `BLEND_OPAQUE` | ― | ― | 描く色そのまま | 不透明な物 |
| `BLEND_LINEAR` | `SRC_ALPHA` | `INV_SRC_ALPHA` | 描く色 × a ＋ 既にある色 ×（1 − a） | 半透明（煙・UI） |
| `BLEND_ADDITIVE` | `SRC_ALPHA` | `ONE` | 描く色 × a ＋ 既にある色 | 光（マズルフラッシュ） |

### sRGB とリニア

- 画像ファイルの色の数（sRGB）は、光の量に比例していない。暗い側を細かく刻むように曲げてある
- 光の計算（足す・掛ける）は、光の量に比例した数（リニア）でしないと合わない
- だから「読むときにリニアへ直し、計算し、画面へ出すときに sRGB へ戻す」
- テクスチャや描画先の形式に `_SRGB` が付いていると、GPU が読むとき・書くときに自動で変換する

## 読むときの問い

### サンプラとテクスチャ

1. コンストラクタで作っているサンプラは 4 つ（`mSamplerStates[ 0 ]`・`[ 1 ]`・`mClampSampler`・`mShadowSampler`）。それぞれ、どんな読み方で、何に使うか
2. `Framework.cpp` の `preUpdate` は 3D の前に `TEXTURE_FILTER_LINEAR`、`postUpdate` は 2D の前に `TEXTURE_FILTER_POINT` にしている。理由は（コメントにある）
3. ミップマップとは何か。無いと遠くの路面はどう見えるか
4. `mWhiteTexture`（白 1 画素）は何のためにあるか（`drawFromVertex` の `if ( !mCurrentTexture ) setTexture( mWhiteTexture );`）
5. `TextureImpl.h` は色空間で形式を `DXGI_FORMAT_B8G8R8A8_UNORM_SRGB` と `DXGI_FORMAT_B8G8R8A8_UNORM` に分けている。色の画像・法線マップ・UI の画像は、それぞれどちらで読むべきか

<details><summary>答え</summary>

1. `[ 0 ]`：点サンプリング・繰り返し。2D や文字（にじませない）。`[ 1 ]`：異方性 16 倍・繰り返し。3D の面。`mClampSampler`（s1）：線形・端で止める。画面の写しを読むとき、端で反対側の色が混ざらないように。`mShadowSampler`（s2）：比較サンプラ。影のマップの深度と比べた結果を返す（09 章）
2. 3D は、浅い角度で見た路面の細い線が、粗いミップでつぶれないよう異方性つきで読む。2D と文字は、画素をにじませないよう点で読む
3. 半分・その半分…と縮めた絵をあらかじめ持っておき、遠くでは小さい絵を読む仕組み。無いと、遠くでは画面の 1 画素にテクスチャの何十画素もが入り、その中の 1 つだけを拾うので、動くたびにちらつく
4. 内蔵のシェーダは「頂点色 × テクスチャ」で色を出す。テクスチャを使わない物でも同じシェーダで描けるよう、何も付いていなければ白（掛けても変わらない）を付ける。分岐やシェーダの種類を増やさないための常套手段
5. 色の画像は SRGB（読むとき GPU がリニアへ直す）。法線マップは色ではなく向きの数なので UNORM（変換されると向きが狂う）。UI は、このコードではバックバッファが UNORM で「画面の色のまま」描くので UNORM（リニア）で読む

</details>

### ブレンドと深度

1. 深度ステンシルステートは 4 つ作ってあり、`applyDepthStencilState` は `( mCurrentDepthTest ? 0 : 2 ) | ( mCurrentDepthWrite ? 0 : 1 )` で選んでいる。4 つの中身を表にできるか
2. 半透明の板（砂ぼこり・血）は、不透明な物を全部描いた**後**に、深度を**書かずに**描いている（`SceneRenderer::render` の `resumeSceneReadOnlyDepth`）。先に描くと・深度を書くと、それぞれ何が起きるか
3. マズルフラッシュは「加算なので順番は問わない」とコメントにある。なぜ加算だと順番が関係ないのか
4. [GBuffer.cpp](../LastDrop/GameSrc/src/Render/Lighting/GBuffer.cpp) の `begin` は、わざわざ `setBlendMode( BLEND_OPAQUE )` している。コメントに理由がある。何が起きていたか
5. `createBlendState` は、1 枚分の設定を 8 枚分すべてに入れている。なぜ 8 枚か
6. `mBlendStates[ 3 ]`（LINEAR_KEEP_ALPHA）は、色は普通に混ぜるが `SrcBlendAlpha = ZERO`・`DestBlendAlpha = ONE`。何のためか

<details><summary>答え</summary>

1. 0：テストする・書く（普通の不透明）。1：テストする・書かない（半透明）。2：テストしない・書く。3：テストしない・書かない（全画面のパス・UI）。テストしないときは比較を `ALWAYS` にしている
2. 先に描くと：後から描く不透明な物が、深度テストに通れば上書きして消す（混ざらない）。深度を書くと：半透明の板の後ろにある別の半透明の板が、深度テストで捨てられて見えなくなる。だから「不透明を全部 → 半透明を奥から順に、深度は読むだけ」
3. 足し算は順番を変えても結果が同じ（a + b = b + a）。普通の半透明の式は「既にある色 ×（1 − a）」が入るので、順番で結果が変わる
4. G-Buffer のアルファは透明度ではなくデータ（予備の 0 や発光の強さ）を入れている。前に描いた物（半透明の板・UI）のブレンドが残っていると、アルファ 0 の画素は「描く色 × 0 ＋ 既にある色 × 1」で何も書かれない。D3D11 は状態機械なので、前の設定が残る
5. D3D11 は描画先を同時に 8 枚まで付けられ（MRT。08 章）、ブレンドの設定は描画先ごとに持てる作りになっている
6. 描画先のアルファを壊さずに色だけ混ぜる。描画先のアルファに別の意味のデータが入っているとき用

</details>

### 色空間

1. [GBuffer.cpp](../LastDrop/GameSrc/src/Render/Lighting/GBuffer.cpp) の `kFormats` は、色を `RGBA8_SRGB`、法線を `RGBA16F`、材質を `RGBA8` にしている。3 つの理由をコメントから読み取る
2. シーンの色は HDR（1 を超えてよい数）で持ち、最後に [Present.hlsl](../LastDrop/Resource/Shader/Present.hlsl) で画面へ写す。`PSMain` の中の順番（ブルームを足す → 露出 → トーンマップ → グレーディング → ビネット → sRGB へ → ディザ）のうち、「リニアでする事」と「0〜1 の色にしてからする事」の境目はどこか
3. `Common.hlsli` の `srgbToLinear` は `pow( c, 2.2 )` ではなく、場合分けのある式。なぜか

<details><summary>答え</summary>

1. 色：8 ビットにリニアのまま入れると、暗い色に使える段が少なくて段差（バンディング）が出る。sRGB なら暗い側が細かい。法線：−1〜1 の数で、8 ビットでは粗く、負の数も入らないので浮動小数。材質：0〜1 の数で色ではないので、sRGB の変換をされると値が狂う
2. トーンマップ（`toneMapAces`）が境目。その前（ブルームを足す・露出を掛ける）は光の量の計算なのでリニアで無限まで。トーンマップで 0〜1 に収めた後に、色の好み（グレーディング・ビネット・赤み）を掛ける。sRGB へ戻すのは一番最後
3. sRGB の正式な式がそうなっている（暗い所は直線、その先は 2.4 乗）。GPU が `_SRGB` のテクスチャを読むときと同じ式にしておかないと、「GPU が変換した色」と「自分で変換した色」が少しずれる

</details>
