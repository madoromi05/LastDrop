# 04 行列・カメラ・定数バッファ

三角形が出たら、次は「動かす・カメラから見る」。そのために、CPU からシェーダへ行列を渡す。
渡す道が**定数バッファ**。ここは「C++ とシェーダで並びを合わせる」という、間違えても何のエラーも出ない所なので、丁寧にやる。

## この章でできるようになること

- ワールド・ビュー・射影の 3 つの行列が、それぞれ何から何への変換か言える
- 定数バッファを作り、毎フレーム書き換えて、シェーダから読める
- C++ の構造体と HLSL の cbuffer の並びを、自分で数えて合わせられる
- チュートリアル（DirectXMath）と自分のコード（GameLib の Math）の、行列の決まりの違いを説明できる

## 座標変換の流れ

```
モデルの中の位置 ──ワールド行列──▶ 世界の中の位置 ──ビュー行列──▶ カメラから見た位置 ──射影行列──▶ クリップ空間
                                                                                                  │ w で割る（GPU がやる）
                                                                                                  ▼
                                                                         画面の画素 ◀──ビューポート── 正規化デバイス座標（x,y: −1〜1　z: 0〜1）
```

頂点シェーダの仕事は「クリップ空間の位置（`SV_Position`）を出す」ことだけ。w で割るのとビューポートは GPU がやる。

## 自分のコードの行列の決まり（チュートリアルと違う所）

ここを知らないと、チュートリアルと自分のコードを見比べたときに必ず混乱する。

| | 自分のコード（GameLib の Math） | 公式のチュートリアル（DirectXMath） |
|---|---|---|
| ベクトルの向き | 列ベクトル。`v' = M × v`（`Matrix34::mul` は `m00*x + m01*y + m02*z + m03`） | 行ベクトル。`v' = v × M` |
| 掛ける順 | 右から先に効く。`射影 × ビュー × ワールド` | 左から先に効く。`ワールド × ビュー × 射影` |
| 平行移動の入る所 | 一番右の列（`m03`・`m13`・`m23`） | 一番下の行（`_41`・`_42`・`_43`） |
| 座標系 | 右手系。カメラは −Z を見る（`setViewTransform` は「注視点 → 視点」を Z 軸にする。射影は `m32 = -1`） | 左手系が多い（`XMMatrixLookAtLH`。カメラは +Z を見る） |
| 表の面 | 反時計回り（`FrontCounterClockwise = TRUE`） | 時計回り |
| シェーダへの渡し方 | 行ごとの `float4` の配列で渡し、シェーダは `dot( 行, 位置 )` で掛ける（[Common.hlsli](../LastDrop/Resource/Shader/Common.hlsli) の `toClip`） | `XMMatrixTranspose` で転置して渡し、シェーダは `mul( 位置, 行列 )` |
| 深度の範囲 | 0（近い）〜1（遠い） | 同じ |

どちらが正しいということは無い。**1 つのプログラムの中で揃っていればよい。**
ミニレンダラは DirectXMath で書く（世の中の資料がほとんどそうなので）。自分のゲームを読むときだけ、この表で読み替える。

`Matrix34` は 3 行 4 列。4 行目はいつも `( 0, 0, 0, 1 )` なので持たない（射影以外の変換は全部これで足りる）。
射影は 4 行目が要るので `Matrix44`。

## 読むときの問い

### 行列

1. `sendMatrices` は `pvwm.setMul( mProjectionViewMatrix, mWorldMatrix )` で 1 つの行列にまとめてから送っている。頂点に最初に効くのはどちらの行列か
2. `sendMatrices` は、ワールド行列の「逆行列の転置」（`itwm`）も作って送っている。何に使うか。なぜワールド行列そのままではだめか
3. `setPerspectiveTransform` の `m32 = -1.f` は何をしているか（ヒント：`Matrix44::mul` で w がどう計算されるか）
4. `nearClip` を 0 にすると何が壊れるか。`nearClip` を小さく・`farClip` を大きくしすぎると何が起きるか
5. [ShadowMap.cpp](../LastDrop/GameSrc/src/Render/Shadow/ShadowMap.cpp) の `spotShadowProjectionView` は、`projectionView.setPerspectiveTransform(...)` の後に `projectionView *= view;` している。掛ける順はこれで合っているか

<details><summary>答え</summary>

1. ワールド行列。列ベクトルの決まりでは、右に書いた行列が先に効く。`( 射影ビュー × ワールド ) × 頂点`
2. 法線の変換に使う（`Common.hlsli` の `normalToWorld`）。物を縦にだけ伸ばすような拡大（軸ごとに倍率が違う拡大）をすると、ワールド行列をそのまま法線に掛けた結果は面に垂直でなくなる。逆行列の転置を掛ければ垂直のまま。回転と、全方向に同じ倍率の拡大だけなら、どちらでも向きは同じ
3. 出力の w を「−（カメラから見た z）」にしている。カメラは −Z を見るので、前にある物の w は正の「奥行き」になる。GPU が x・y・z を w で割ることで、遠い物ほど小さくなる（遠近）
4. 0 だと、式の `b = nearClip * a` が 0 になり、どの距離の点も w で割った後の深度が 1 になる（前後の区別が付かない）。near が小さすぎ・far が大きすぎると、深度の細かさがほとんど near の近くに使われ、遠くの面どうしが前後を取り違えてちらつく（Z ファイティング）
5. 合っている。`A *= B` は `A = A × B`（`Matrix44::operator*=` の中身で確かめられる）なので「射影 × ビュー」。頂点にはビューが先に効く

</details>

### 定数バッファ

1. `ConstantBufferImpl.h` のコンストラクタの `mSize( ( byteSize + ALIGNMENT - 1 ) / ALIGNMENT * ALIGNMENT )` は何の計算か。なぜ要るか
2. `set` の `Map` → `memcpy` → `Unmap` は、それぞれ何をしているか
3. `setWorldMatrix` は値を覚えて `mMatricesChanged = true` にするだけで、GPU へは送らない。送るのはいつか。なぜそうしているか
4. `setConstantBuffer` は `VSSetConstantBuffers` と `PSSetConstantBuffers` の両方を呼んでいる。では内蔵の b0 はどうなっているか（`setInitialStates` と、`Lighting.hlsli` の `cbuffer PSConstants` のコメント）
5. [SkinningPipeline.cpp](../LastDrop/GameSrc/src/Render/SkinnedMesh/SkinningPipeline.cpp) の `begin` は「使う骨のぶんだけ送る。残りの中身は不定になる」と書いてある。なぜ残りは「前の値のまま」ではなく「不定」なのか
6. HLSL の cbuffer に `float3 a; float b; float3 c; float3 d;` と書くと、C++ 側では何バイト目に何が来るか

<details><summary>答え</summary>

1. 16 の倍数への切り上げ。定数バッファの大きさは 16 バイトの倍数でないと `CreateBuffer` が失敗する
2. `Map`：GPU 側のバッファに書き込むための場所（ポインタ）を借りる。`memcpy`：そこへ CPU 側の構造体を写す。`Unmap`：書き終わったと知らせて返す。`WRITE_DISCARD` は「前の中身は捨てる」
3. 次の `draw` の直前（`drawFromVertex`・`prepareIndexedDraw` の `if ( mMatricesChanged ) sendMatrices();` と `flushConstantBuffers`）。1 回の描画の前に行列を何度変えても、送るのは 1 回で済む。同じ値を入れ直したときは送らない（`if ( mWorldMatrix != m )`）
4. 頂点シェーダの b0 とピクセルシェーダの b0 は**別の物**。番号はシェーダの段ごとに別々にある。内蔵では VS の b0 に `mVSCB`（行列など）、PS の b0 に `mPSCB`（ライトなど）を付けている。自作（b1 から）は、同じバッファを両方の段に付けている
5. `WRITE_DISCARD` で `Map` すると、GPU は新しい場所を渡すことがある（前の場所は、まだ前の描画が使っているかもしれないので）。新しい場所の、書かなかった部分には何が入っているか分からない
6. `a` が 0〜11、`b` が 12〜15（a の後ろの空きに入る）。`c` が 16〜27。`d` は 28 からだと 16 バイトの区切りをまたぐので、32 へ飛ばされて 32〜43。28〜31 は空き。全体は 48 バイト。「1 つの変数は 16 バイトの区切りをまたげない」が決まり

</details>

### 課題 04-2：並びの食い違いを自分で見つける（実際のコードの調査）

本当に同じか、自分で数えて確かめる。

やり方：

1. C++ 側のメンバーを上から順に、float 4 つずつ（16 バイトずつ）に区切って表に書く
2. HLSL 側の `float4` の `.x`・`.y`・`.z`・`.w` を、同じ表の隣に書く
3. 1 つずつ名前を見比べる。シェーダの `applyPuddle` が、どの成分を何として使っているかも見る
4. 食い違いがあるなら、「今、画面ではどう見えているはずか」を予想する
5. F6 のエディタで予想を確かめる（Render タブで G-Buffer の表示を Roughness にして、Tuning の水たまりの値を 1 つずつ動かす）

<details><summary>答え（自分で表を書いてから開く）</summary>

教材を書いた AI が 2026-11-12 にコードを読んだ時点では、食い違っている（画面では確かめていない。自分で確かめること）。2026-11-14 に読み直しても同じだった。

| 4 | `wetBand` | `gPuddleShape.y` | 濡れた縁の幅 ✔ |
| 8 | `inverseTileSize` | `gPuddleShape.z` | 1 / 模様の大きさ ✔ |
| 12 | `puddleRoughness` | `gPuddleShape.w` | **使わない** |
| 16 | `wetRoughness` | `gPuddleSurface.x` | **水たまりの粗さ**として使う ✘ |
| 20 | `wetDarkening` | `gPuddleSurface.y` | **濡れた路面の粗さ**として使う ✘ |

C++ 側は `inverseTileSize` の後ろに 1 つ空きを入れ忘れ、代わりに `wetDarkening` の後ろに 2 つ空きを入れている。
全体の大きさ（48 バイト）は合っているので、後ろの `motion` は正しい所に入り、エラーも警告も出ない。

予想される見え方（`PuddleParams.h` の初期値で）：

- 水たまりの粗さは 0.05 のつもりが 0.4（`wetRoughness` の値）。鏡のようにならない
- 濡れた路面の粗さは 0.4 のつもりが 0.6（`wetDarkening` の値）
- 濡れた所の色は 0.6 倍のつもりが 0 倍。濡れた所と水たまりの色が真っ黒になる

直し方は、C++ 側の並びを HLSL に合わせる（`inverseTileSize` の後ろに空きを 1 つ、`wetDarkening` の後ろの空きを 1 つに）。
直すと見た目が変わる（今の見た目で調整値を決めていたなら、値も決め直す）ので、直す前に今の絵をスクリーンショットで残す。

これが「定数バッファの並びは、間違えても誰も教えてくれない」の実例。防ぐ方法を 3 つ考える
（例：`float4` 単位の構造体で書く／`static_assert( offsetof( PassConstants, motion ) == 32 )` を置く／シェーダのリフレクションで並びを確かめる）。

</details>

### 課題 04-5：2 か所に書いてある「同じ数」を確かめる（実際のコードの調査）

配列の大きさのように、C++ とシェーダの**両方に同じ数を書く**所がある。コメントには「揃える」と書いてあるが、揃っているかを確かめる仕組みは無い。
次の 4 組を、自分で両方のファイルを開いて見比べる。

| C++ 側 | シェーダ側 |
|---|---|
| `SkinningPipeline.h` の `kMaxBones` | `Skinning.hlsli` の `MAX_BONES` |
| `StaticMeshInstancing.h` の `kMaxInstances` | `StaticMeshInstancing.hlsli` の `MAX_INSTANCES` |
| `LightList.h` の `kMaxShadowMaps` | `LightList.hlsli` の `kMaxShadowMaps` |
| `LightList.h` の `kMaxLights` | `LightList.hlsli` の `kMaxLights` |

食い違っている組があれば、次を考える。

1. C++ 側が大きいとき・シェーダ側が大きいとき、それぞれ何が起きるか（定数バッファの中で、その配列が**最後**にあるか**途中**にあるかで変わる）
2. 画面ではどう見えるはずか。シェーダが数をどう使っているかを読む（`Pbr.hlsli` の `shadeSurface`）
3. 2 か所に書かずに済ませる方法・食い違いをビルドで見つける方法はあるか

<details><summary>答え（自分で見比べてから開く）</summary>

教材を書いた AI が 2026-11-14 に読んだ時点では、`kMaxLights` だけ食い違っている（C++ が 20、シェーダが 16）。ほかの 3 組は同じ。画面では確かめていない。

1. 配列が cbuffer の**最後**にあるので、後ろの変数がずれることは無い（`gLights` の後ろには何も無い）。途中にある配列の大きさが違うと、それより後ろの変数が全部ずれる（課題 04-2 と同じ種類の不具合になる）
2. C++ 側は、ライトを 20 個まで選んで送り、数も 20 と伝える。シェーダは `min( 数, kMaxLights )` で 16 に切ってから回すので、**17 個目から後ろは照らされない**。送った並びの後ろの 4 つが、選ばれたのに光らない（どの光が後ろに来るかは、`LightList.cpp` の選び方を読んで確かめる）。エラーも警告も出ない
3. 例：シェーダをコンパイルするときに、C++ の定数を `#define` として渡す（`D3DCompile` の引数にマクロを渡せる）／シェーダのリフレクションで配列の大きさを読み、起動時に `ASSERT` で比べる／数を 1 つのヘッダに書き、C++ とシェーダの両方から読む

直すなら、どちらの数に合わせるかを先に決める（ライトを増やすと、ライティングのパスが重くなる。`SummaryPlan/計測の記録.md` の⑦に「ライト 1 個で約 0.03ms」とある）。

</details>
