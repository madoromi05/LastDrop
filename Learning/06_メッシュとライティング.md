# 06 メッシュとライティング

立方体から、建物や車のような「メッシュ」へ。そして光を当てる。
ライティングは「法線と光の向きの内積」という 1 行から始まり、PBR（08 章）もその延長にある。

## この章でできるようになること

- インデックスバッファを使ってメッシュを描ける
- ランバート（拡散）と鏡面の式を、シェーダに自分で書ける
- 頂点シェーダとピクセルシェーダのどちらで何を計算するかを決められる
- インスタンシングとカリングが、何を減らすための物か言える

## 式

光の向きを `L`、法線を `N`、目の向きを `V`（どれも長さ 1。面から外へ向かう向き）とする。

```
拡散（ランバート）  = 面の色 × 光の色 × max( 0, dot( N, L ) )
鏡面（フォン）      = 光の色 × pow( max( 0, dot( R, L ) ), 鋭さ )      R = V を N で反射した向き
鏡面（ブリン・フォン）= 光の色 × pow( max( 0, dot( N, H ) ), 鋭さ )    H = normalize( L + V )
```

点光源は、距離の 2 乗で弱くなる（`1 / 距離²`）。

## 読むときの問い

### メッシュ

1. 立方体は、頂点バッファだけなら 36 頂点、インデックスバッファを使うと頂点はいくつ・インデックスはいくつか。ただし面ごとに法線を変えたいなら頂点はいくつ要るか
2. インデックスは 16 ビット（`unsigned short`）。1 つのメッシュで使える頂点の数の上限は。超えるモデルを読むとどうなるか（`tools/convert` の側か、読む側で何か対策があるか探す）
3. `StaticMeshPart::upload` は、GPU へ送った後に `mStagingVertices.clear()` している。一方で `mShape.set( positions, triangleIndices )` で位置だけ残している。それぞれ理由は
4. 「設計図（`StaticMeshData`）」と「1 つぶん（`StaticMeshInstance`）」を分けると、同じ建物を 50 軒置いたとき、GPU のメモリには頂点が何軒ぶんあるか。この分け方の名前は
5. `StaticMeshPart::draw` は、G-Buffer と影のパスの間だけ `m.setShader( RenderPass::staticMeshShader() )` している。同じメッシュを、パスごとに違うシェーダで描いている。なぜそれができるか（頂点バッファとシェーダの関係）

<details><summary>答え</summary>

1. 頂点 8・インデックス 36。ただし面ごとに法線を変える（角をくっきりさせる）なら、同じ位置でも法線が違う頂点は別の頂点なので 24（6 面 × 4）。UV も同じで、「位置・法線・UV の全部が同じ」ときだけ頂点を共有できる
2. 65536。16 ビットなのはメモリが半分で済むため。超えたときの扱いは自分で確かめる（部品に分ける・32 ビットにする、のどちらかが普通）
3. 頂点は GPU に送れば CPU 側では要らない（建物 1 つで数百 KB ある）。ただし弾の当たり判定（三角形との交差）は CPU でやるので、位置とつながりだけは残す。UV・法線・色は判定に要らないので捨てる
4. 1 軒ぶん。置き場所の行列だけが 50 個ある。Flyweight（全員で同じ部分は 1 つだけ持つ）。技術まとめの 6-2
5. 頂点バッファはただのデータで、シェーダとは別の物。入力レイアウトが合っていれば、どのシェーダでも同じ頂点を読める。G-Buffer 用は材質を 3 枚に書き、影用は深度だけ書く。メッシュを 2 つ持つ必要は無い

</details>

### ライティング

`PixelLightingPsHlsl.h` の `main` を読む。4 つの光を `float4` の x・y・z・w に入れて、4 つ同時に計算している。

1. `ev`・`nv`・`rv`・`lvX/Y/Z` は、上の式の `V`・`N`・`R`・`L` のどれか
2. `d = ( lvX * nv.xxxx + ... ) * rcpLvL * rcpLvL;` で `rcpLvL`（1 / 距離）を 2 回掛けている。1 回は何のため、もう 1 回は何のためか。本当の物理（距離の 2 乗で弱くなる）と合っているか
3. `s = pow( s, gSpecularColor.w );` の `w`（鋭さ）を大きくすると、ハイライトはどう変わるか
4. 頂点シェーダから渡された法線 `p.wnorm` を、ピクセルシェーダで `normalize` し直している。なぜ要るか
5. 頂点ごとのライティング（`VertexLightingVsHlsl.h`）と、ピクセルごとのライティングは、見た目と重さがどう違うか
6. 4 つの光を「ループで 4 回」ではなく「`float4` で 1 回」で計算している。何が嬉しいか。逆に何が不便か

<details><summary>答え</summary>

1. `ev` が V（正規化はしていない。面から目へ）、`nv` が N、`rv` が R（V を N で反射した向き）、`lvX/Y/Z` が 4 つの光それぞれの L（面から光へ。正規化前）の x・y・z 成分
2. `lv` は正規化していないので、`dot( lv, nv )` は「距離 × cos」になっている。1 回目の `rcpLvL` で長さを消して cos にし、2 回目で距離による減衰を掛けている。つまり減衰は `1 / 距離`。本当の物理（`1 / 距離²`）とは違う（古い作りの簡易版）。PBR の方（`Pbr.hlsli` の `evaluateLight`）がどうしているか見比べる
3. 小さく鋭くなる（つるつるに見える）。小さくすると広くぼやける（ざらざらに見える）
4. 頂点シェーダの出力は、三角形の中で**線形に補間**されてピクセルシェーダへ来る。長さ 1 の法線どうしを補間すると、間では長さが 1 より短くなる
5. 頂点ごと：色を頂点で計算して補間する。軽いが、頂点の粗いメッシュでは、三角形の真ん中に来るハイライトが出ない。ピクセルごと：法線を補間して画素ごとに計算する。重いが正確。今の GPU ではピクセルごとが普通
6. GPU は `float4` の計算を 1 回の命令でできるので速い。不便な点は、光の数が 4 に固定されること・コードが読みにくいこと。PBR の方はライトの一覧をループで回している（`Pbr.hlsli` の `shadeSurface`）

</details>

### 法線マップ・インスタンシング・カリング

1. `Lighting.hlsli` の `perturbNormal` は、頂点に接線（タンジェント）を持たせずに、`ddx`・`ddy` で接線を作っている。`ddx( worldPosition )` は何を返すか。この方法の良い所・悪い所は
2. `perturbNormal` は、法線マップの x・y だけを読んで z は `sqrt( 1 - x² - y² )` で作っている。なぜそれができるか。何が嬉しいか（BC5 と関係がある）
3. `StaticMeshInstancing.cpp` は、置き場所の行列を**定数バッファ**（128 軒ぶん）に入れ、シェーダが `SV_InstanceID` で引いている。インスタンシングで減るのは何か。減らないのは何か
4. `placeVector` のコメントに「建物は等倍で置くので、逆行列の転置ではなく行列の 3x3 でそのまま回せる」とある。04 章のどの話か
5. `ViewFrustum` のコンストラクタは、射影ビュー行列の「行の足し算・引き算」で 6 枚の面を作っている。`w + x >= 0` が「左の面より内側」になるのはなぜか
6. `mayContain` は、箱の 8 つの角を全部調べず、面ごとに 1 つの角だけ調べている。どの角か。なぜそれで足りるか

<details><summary>答え</summary>

1. 画面で右隣の画素との、ワールド位置の差。位置と UV の画面での変化から、「UV の u が増える向き」がワールドでどちらかを逆算できる。良い所：頂点のデータが増えない・モデルを変換するときに接線を作らなくてよい。悪い所：画素ごとに計算が増える・三角形の境目で接線が少し不連続になる・UV の面積が 0 の所で壊れる（最後の `isnan` の行で元の法線へ逃がしている）
2. 法線は長さ 1 で、面から外を向く（z が正）と決まっているので、x と y が分かれば z は決まる。2 チャンネルで済むので、2 チャンネル専用の圧縮形式 BC5 を使えて、画質が良い
3. 減るのはドローコールの数（CPU がドライバーへ頼む回数と、その前の定数の送り直し）。減らないのは GPU が処理する頂点と画素の数。だから技術まとめの数字でも、CPU の描画は大きく減り、GPU はあまり変わっていない
4. 法線の変換。軸ごとに倍率の違う拡大が無ければ、ワールド行列の回転の部分をそのまま掛けてよい
5. クリップ空間で画面に映るのは `-w <= x <= w`。左の端は `x >= -w`、つまり `w + x >= 0`。x も w も「行列の行 × 点」なので、`( w の行 + x の行 ) × 点 >= 0` と書ける。これは平面の式そのもの（Gribb と Hartmann の方法）
6. その面の法線の向きへ一番寄った角。それが外側にあるなら、ほかの 7 つの角はもっと外側なので、箱はまるごと外。1 面につき 1 回の内積で済む

</details>
