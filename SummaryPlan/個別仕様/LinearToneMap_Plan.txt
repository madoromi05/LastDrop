 2. 進め方（1-a と 1-b に分ける）
================================================================================

 1-a  リニア化 ＋ ToneMap（TGA のまま）
   (1) 計測：今の絵のスクリーンショット（決まった場面。F6 の Snapshot で同じ場所を出す）
       と、F7 の CSV・load_*.json を取っておく（比べる元）
   (2) GameLib：Texture に「色の画像か」の指定を足す。色の画像は _SRGB で作り、ミップをリニアで平均する
   (3) GameSrc：材質・エフェクトの読み込みで、アルベドとエフェクトの画像を「色」として読む
   (4) シェーダ：頂点色・材質の色・ライトの色・環境光をリニアへ直す（5 章）
   (5) Present.hlsl：露出 → ACES → ビネットなど → ガンマ（6 章）
   (6) F6 に「Render」欄を足し、露出・ブルームの値を調整する（7 章）
   (7) 確かめる（10 章）
 1-b  DDS と大きさの見直し
   (1) texconv で DDS を作るツール（8-1）
   (2) GameLib に DDS の読み込み（8-4）
   (3) 法線マップを BC5 にしたので、シェーダで z を作り直す（8-2）
   (4) メッシュのファイルに書かれた画像の名前を .dds にする（8-5）
   (5) 確かめる（10 章。絵が 1-a と同じ・メモリと読み込み時間が減る）

 分ける理由：1-a は「絵が変わる」、1-b は「絵は変わらず読み込みとメモリが変わる」。
 一緒に入れると、絵がおかしいときに sRGB の指定のせいか圧縮のせいか分からない。

 3. 色の画像と色ではない画像の区別（sRGB として読む）
================================================================================
 sRGB として読む画像は、GPU が読むときにリニアへ直してくれる（線形のフィルタもリニアで掛かる）。

  画像                                   読み方
  -------------------------------------  ----------------------
  アルベド（*_albedo.tga）               sRGB（色）
  エフェクト（砂ぼこり・血・弾痕・       sRGB（色）
    マズルフラッシュの芯とにじみ）
  法線マップ（*_normal.tga）             そのまま（色ではない）
  HUD・フォント（バックバッファへ直接）  そのまま（ガンマの画像をそのまま出す）

 ・GameLib：Texture::create に「色の画像か」を渡せるようにする。
   bool ではなく enum にする（呼ぶ所で意味が読めるように）
     enum TextureColorSpace { TEXTURE_COLOR_SPACE_LINEAR, TEXTURE_COLOR_SPACE_SRGB };
   既定は LINEAR（今と同じ）。HUD・フォントなど今ある呼び出しは何も変えずに今のまま動く
 ・GameSrc：TextureCache::load に同じ指定を足す。キャッシュの鍵は「ファイル名 ＋ 指定」
   （同じ画像を色と色以外で読むことは無い予定だが、混ざったら ASSERT で止める）
 ・指定する所
     MeshLoaderUtil::loadMaterial … アルベドは SRGB、法線は LINEAR（どちらの画像か分かっている所）
     BloodSprayList・ImpactDustList・BulletHoleList・MuzzleFlash … SRGB

================================================================================
 4. ミップの作り方（1-a。TGA のとき）
================================================================================
 今は 4 画素をガンマのまま平均している。色の画像をこのまま _SRGB で読むと、遠くの縮んだ
 絵が少し暗くなる（ガンマのまま平均すると暗い側へ寄る）。
  ・色の画像：4 画素をリニアへ直して平均し、ガンマへ戻して書く（アルファはそのまま平均）
  ・色ではない画像：今のまま
  ・リニアとガンマの変換は表（256 個）を 1 回だけ作って引く（読み込みが遅くならないように）
 1-b の DDS は texconv がリニアで平均したミップを入れるので、この処理は TGA のときだけ通る。

================================================================================
 5. シェーダで色をリニアへ直す所
================================================================================
 テクスチャ以外の色は、人が「画面の色」として選んだ数なので、計算の前にリニアへ直す。
 C++ の値（GameScene・材質の txt・頂点色）は今のまま変えない（選んだ色の意味が変わらない）。

  色                                         直す所
  -----------------------------------------  ------------------------------------------
  頂点色（COLOR）                            頂点シェーダで読んだ直後
  材質の色（diffuse / specular の色）        ピクセルシェーダで使う直前
  ライトの色・環境光                         ピクセルシェーダで使う直前
  エフェクトの色（LitQuadBatch の頂点色）    頂点色と同じ
  明るさ・強さ・粗さなど色ではない数         直さない

 ・変換の関数は共通にする：Resource/Shader/Common.hlsli に srgbToLinear / linearToSrgb
   （GameLib に埋め込んだ HLSL は Common.hlsli を読めないので、同じ式を GameLib 側にも 1 か所置く）
 ・ライトの「強さ / 距離」の減衰の式は変えない（段階 3 の PBR で作り直す）
 ・ブルームの取り出し（BloomExtract.hlsl）は式を変えない。リニアの値に対してしきい値 1 で切る

================================================================================
 6. 画面へ写す（Present.hlsl：露出・ToneMap・ガンマ）
================================================================================
 順番（Graphics_Spec.txt 2 章の (10)。カラーグレーディングとディザは段階 5 でこの間に入れる）

   シーンの色（痛みのぼかし込み）
   ＋ ブルーム × 強さ
   × 露出
   → ACES 近似（Narkowicz の式）     0〜無限 を 0〜1 へなだらかに
   → ビネット・噛まれた赤み・暗転    今と同じ式。ToneMap の後（0〜1 の色に掛けるので量が今と同じ意味になる）
   → linearToSrgb（ガンマを掛ける）
   → バックバッファ

 ・ACES 近似（Narkowicz 2016）：
     f(x) = saturate( (x(2.51x + 0.03)) / (x(2.43x + 0.59) + 0.14) )
   0.6 を掛けてから通す版もあるが、露出の初期値 1.0 で始めて画面で合わせる
 ・赤み（gFlashColor）は C++ で選んだ画面の色なので、ToneMap の後・ガンマの前に混ぜるときは
   リニアへ直してから混ぜる
 ・PresentConstants に露出（gExposure）を 1 つ足す（今の gPadding の所に入れれば並びが崩れない）

================================================================================
 7. 値の調整（F6）
================================================================================
 リニアにすると絵全体が暗く・コントラストが強く見えるはず。下の値を F6 で合わせ直す。
  ・F6 に「Render」欄を足す（AimSwayParams などと同じ visit の形。名前・値・範囲・単位）
      露出（初期値 1.0）、ブルームのしきい値（1.0）と強さ（0.5）
  ・環境光・ライトの色と強さは GameScene の定数のまま。足りなければ同じ欄へ足す
  ・合わせる目標：今の絵より暗い所がつぶれず、マズルフラッシュの芯に色が残る
    （夜の暗さはまだ作らない。段階 3 のライトと段階 5 のカラーグレーディングで作る）
  ・決まった値は Copy as C++ でコードの初期値にする

 8. 1-b：DDS（BC 圧縮）と大きさの見直し
================================================================================

--------------------------------------------------------------------------------
 8-1. DDS を作るツール
--------------------------------------------------------------------------------
  ・texconv（Microsoft の DirectXTex に付いているコマンド）を tools/ のスクリプトから呼ぶ
    （tools/texture_to_dds.bat。TGA を Resource/ に残し、横に .dds を書く。元は消さない）
  ・色の画像   ：texconv -f BC7_UNORM_SRGB -srgbi -m 0 -y -o <出力先> <画像>
  ・法線マップ ：texconv -f BC5_UNORM -m 0 -y -o <出力先> <画像>
  ・-m 0 でミップを全段作る（リニアで平均してくれる）
  ・texconv.exe はリポジトリに入れず、置き場所をツールの先頭に書く（無ければ止まって知らせる）

--------------------------------------------------------------------------------
 8-2. 形式
--------------------------------------------------------------------------------
  画像               形式              1 画素     元（BGRA8）との比
  -----------------  ----------------  ---------  ---------------
  色（アルファ有無）  BC7_UNORM_SRGB    1 byte     1/4
  法線マップ          BC5_UNORM         1 byte     1/4（x と y だけ持つ）
  （候補）色・アルファ無し  BC1_UNORM_SRGB  0.5 byte   1/8（BC7 より少し荒い。画面で比べてから）

  ・BC5 は法線の x と y だけ持つので、シェーダで z = sqrt( saturate( 1 - x² - y² ) ) を作り直す
    （GameLib の PixelLightingNormalMapPsHlsl.h と Lighting.hlsli の 2 か所）
  ・法線マップは全部同時に BC5 にする（TGA と混ざると z の作り方が合わなくなる）

--------------------------------------------------------------------------------
 8-3. 大きさの見直し
--------------------------------------------------------------------------------
  ・ゾンビ（3,610 三角形）の 4096² は 2048² にする（1/4。Optimization_Plan 7-3 (b)）
  ・ほかの 4096² は、画面に映る大きさで見比べて決める（未決事項）
  ・texconv の -w / -h で縮める。元の TGA は縮めない（後から戻せるように）

--------------------------------------------------------------------------------
 8-4. GameLib の DDS の読み込み（自前）
--------------------------------------------------------------------------------
  ・読む物：DDS の頭（DDS_HEADER）と DX10 の追加の頭（DDS_HEADER_DXT10）、ミップの段
  ・対応する形式：BC1 / BC5 / BC7（と、その _SRGB）。それ以外は ASSERT で止める
    （対応していない形式を黙って変に描くより、止めて知らせる）
  ・作り方は今の TGA と同じく「空で作って UpdateSubresource で書く」
    （TextureImpl.h のコメントの Intel Iris Xe の不具合の回避を BC でもそのまま使う）
    1 行の幅はブロック（4×4 画素）の数 × ブロックの大きさ（BC1 は 8 byte、BC5・BC7 は 16 byte）
  ・拡張子で TGA と DDS を分ける（Texture::create の入口は 1 つのまま）
  ・色の画像か（3 章の指定）は DDS の形式が _SRGB かどうかで決まる。指定と合わなければ ASSERT

--------------------------------------------------------------------------------
 8-5. 画像の名前の書き換え
--------------------------------------------------------------------------------
  ・メッシュのファイル（*.txt）に書かれた画像の名前を .tga → .dds にする
  ・tools/fbx_to_gamelib.py の出力も .dds にする（作り直したときに .tga へ戻らないように）
  ・エフェクトの画像の名前（kTextureFile など）も .dds にする
  ・「.dds があればそちらを読む」という隠れた決まりは作らない（どの画像を読んでいるかが
    ファイルを見れば分かるように）

 10. 確かめ方
================================================================================
  1-a
  ・決まった場面（F6 の Snapshot）で、前後のスクリーンショットを並べる
      暗い所（建物の陰・車の下）がつぶれていない
      明るい所（マズルフラッシュの芯・ブルーム）が白一色ではなく色が残る
      遠くのテクスチャ（ミップ）が手前より暗くなっていない
      HUD・文字・ImGui の色が前と同じ
  ・F7 の CSV の GPU の時間がほぼ同じ（変換の分だけ。増えても 0.1ms 以下の見込み）
  1-b
  ・同じ場面のスクリーンショットが 1-a とほぼ同じ（圧縮のにじみ・縞が目立たない）
  ・GPU のメモリ：約580MB → 約100〜150MB（計算値。読み込んだ画像の大きさの合計を出力して確かめる）
  ・ロード時間（load_*.json）：今の 1.12 秒から縮む（CPU でミップを作らなくなる分）
  ・比べた数字は 技術まとめ_ポートフォリオ.md と報告書に書く

 11. 懸念点
================================================================================
  ・見た目の調整のやり直し：絵全体が変わるので、ブルーム・マズルフラッシュ・痛みの赤みなど、
    画面確認待ちの物の値は 1-a の後で見直すことになる
  ・GameLib の埋め込み HLSL と Resource/Shader の HLSL に同じ変換の式が 2 か所できる
    （段階 2 で固定パイプラインを自作シェーダへ移すと 1 か所になる。それまではコメントで互いを指す）
  ・BC7 の圧縮は遅い（4096² 1 枚で数十秒〜）。ツールは画像を足したときだけ走らせる（起動時ではない）
  ・Intel の内蔵 GPU：今の TGA で白く見える不具合があった（TextureImpl.h のコメント）。
    BC でも起きないか、内蔵 GPU の PC で 1 回確かめる
  ・SkinTestScene などテスト用のシーンも同じ読み込みを通るので、一緒に色が変わる（直さなくてよい）

 13. 1-a の実装メモ（2026-10-26。仕様から変えた所）

  ・色の定数（ディフューズ・スペキュラ・発光・アンビエント・ライト）は、シェーダではなく GameLib の
    ManagerImpl::sendLightingParameters で 1 回だけリニアへ直して b0 に入れる

  ・直すかどうかは Graphics::Manager::enableLinearColor( bool )。PostProcess::beginScene で入れ、endScene で切る
    （固定パイプラインのシェーダは HUD・文字も描くので、いつも直すと HUD の色が変わるため）
  ・頂点色だけは頂点シェーダで直す（b0 の c19 に gColorParams を足した。x が 1 なら直す）
      固定パイプライン：GameLib/src/Graphics/ColorSpaceHlsl.h の vertexColorToScene（3 本の頂点シェーダの前につなぐ）
      自作シェーダ　　：Resource/Shader/Common.hlsli の vertexColor
  ・1 を超える色（LitQuadBatch のマズルフラッシュの芯の 3 倍など）は「1 以下の色 × 倍率」とみなし、倍率は直さない
    （GameLib/src/Graphics/ColorSpace.h。全体を式に通すと 3 が 14 倍になる）
  ・F6 の値は「Render」欄ではなく、Tuning の中の PostProcessParams にした（露出・ブルームのしきい値・強さ）
    （プリセットの保存・読み込み・Copy as C++ がそのまま使えるため。GameSrc/Render/PostProcessParams.h）
    ブルームのしきい値と強さも Bloom.cpp・PostProcess.cpp の定数からここへ移した（初期値は同じ 1.0・0.5）
  ・ミップの平均は 8bit → 16bit のリニアの表と、リニアの上 12bit → 8bit の表で引く（TextureImpl.h の SrgbTables）
  ・PostProcess を通らない SkinTestScene（テスト用）はアルベドだけリニアで読まれて暗く見える。直さない（11 章のとおり）

 14. 1-b の実装メモ（2026-10-27。仕様から変えた所と、測った数字）

  ・変換のツールは .bat ではなく tools/texture_to_dds.ps1（画像ごとに 色 / 法線・縮める大きさ を表で書けるため）
      pwsh -File tools/texture_to_dds.ps1 [名前の一部]
    texconv.exe の置き場所は %USERPROFILE%\Tools\DirectXTex\texconv.exe（環境変数 TEXCONV で変えられる）
    2026-10-27 に GitHub の Microsoft/DirectXTex の最新版（2026.5.8.1）を置いた。署名は Microsoft で有効
    -dx10 を必ず付ける（GameLib は DX10 の頭の DDS だけを圧縮の DDS として読む）
    GPU（DirectCompute）で圧縮され、22 枚で約 9 秒
  ・BC5 の z を作り直す処理は足さなかった。シェーダはもともと法線マップの x と y だけを読み、z を作り直していた
    （PixelLightingNormalMapPsHlsl.h・Lighting.hlsli の perturbNormal）
  ・GameLib：GameLib/src/Graphics/DdsReader.h（ファイルを読むだけ。BC1 / BC5 / BC7 とその _SRGB、ミップ）
    TextureImpl::readDDS が DX10 の頭を見て readCompressedDds へ分ける。古い形（圧縮していない DDS）は今までどおり
    DDS が _SRGB かどうかと、読むときの指定（TextureColorSpace）が食い違えば ASSERT
    圧縮した絵は write（デバッグの書き出し）で読み戻さない（createStagingReadback が nullptr を返す）
  ・画像を GPU へ送るたびに、出力ウィンドウへ「Texture: upload <名前> <大きさ> BC|BGRA8 <KiB> (total <MiB>)」を出す
  ・メッシュのファイル（Resource/*.txt 19 個）の画像の名前を .dds にした。tools/fbx_to_gamelib.py は
    設定の .tga（書き出す元の画像）をそのまま書き出し、メッシュのファイルには .dds の名前を書く（game_texture_path）
  ・エフェクト 5 枚も DDS にした。tools/*_gen.py で作り直したら、texture_to_dds.ps1 も走らせ直す
  ・大きさ：ゾンビの 2 枚だけ 4096² → 2048²。建物・道路の 4096² はまだそのまま（画面で見比べて決める）

  数字（計算値。DDS は BC 圧縮なので、ファイルの大きさ＝GPU のメモリ）
