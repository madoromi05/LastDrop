 Q1. 進め方
     ★A：a・b・c をまとめて入れ、F6 → Render の「Light culling」の入/切を、同じ起動・同じ場所で続けて録る
          ・切の間は今と同じ計算になる（c で上限を揃えても、シェーダが使う数は 30 のままなので GPU の仕事は同じ）
          ・ライティングの重さは、入れた後は「近くに街灯が何本あるか」で場面ごとに変わる。別の起動だと場所が揃わないので、
            同じ起動で入/切を比べる（⑥で起動が別で場面が揃わなかった反省）
      B：回数の印だけ先に入れて「前」を録り、実装の後に別の起動で「後」を録る（⑬〜⑯と同じ）

 Q2. 切り替えの単位
     ★A：a（シェーダで届く距離の外を飛ばす）と b（画面に届かないライトを一覧から外す）を 1 つの切り替えにする
          ・どちらも「絵を変えずに、照らさない計算を省く」同じ目的。分けると切り替えとシェーダの分岐が 1 つずつ増える
          ・b の効きは回数（Light.selected が何本減ったか）で言う
      B：a と b を別々の切り替えにする（どちらが何 ms 効いたかを時間で分けて言える）

 Q3. 照らす数の上限の不一致（LightList.h は 40・LightList.hlsli は 30）
     ★A：C++ を 30 に揃える。シェーダは今も 30 個しか読んでいないので、絵は変わらない
      B：両方を 40 に上げる（今は照らしていない遠い街灯も照らすので、絵が変わる。この作業では見た目を変えないので別にする）

 Q4. スポット（懐中電灯）の角度の外
     ★A：見ない。届く距離（25m）だけで飛ばす
          ・懐中電灯は 1 つだけ。角度の外では、影のマップを読む処理（3×3 の PCF）は今も飛ばしている（evaluateLight の attenuation > 0）
      B：角度の外も飛ばす（届く距離の中の画素の大半を占める。ただし式が 1 つ増える）

 1. ほかのエンジンでは
================================================================================
 ・Unity の Built-in のディファード：点・スポットのライトを、届く範囲の形（球・円すい）の板として描く。
   範囲の外の画素はライトの計算そのものが走らない
 ・Unreal Engine・Doom（2016）など：画面をタイルや奥行きの区切り（クラスター）に分け、区切りごとに届くライトの一覧を作る
   （Tiled / Clustered）。画素はその一覧だけを回す
 ・この作業は、その手前の段。「画素ごとに届く距離で飛ばす」と「画面に届かないライトを CPU で外す」だけで、
   シェーダの作り（全画面を 1 回なぞる）は変えない
 ・ゲームの仕様ではなく描き方の最適化なので、タルコフは調べていない

================================================================================
 2. 今のコードと今の数字
================================================================================
 ・Pbr.hlsli の shadeSurface：すべての画素で、一覧のライト（最大 30 個）の evaluateLight を最後まで計算している。
   届く距離の外では、届く距離の窓（saturate( 1 − (d/range)⁴ )）が 0 になるので、足しても 0。それでも GGX の計算はしている
 ・LightList::select：全部のライトを「平行光 → 届く範囲のふちが目に近い順」に並べ、40 個で切る。画面に映るかは見ていない
 ・ライトの候補：街灯 52 本・月・懐中電灯・マズルフラッシュ。停電の日の街灯は SceneLights が足さない（明るさ 0）
 ・街灯の届く距離は 12m（LightingParams::streetLightRange）。1 つの画素に届く街灯は、多くて 2〜3 本のはず
 ・数字（Profile・中央値）
   | | ライトの上限（シェーダ） | gpu.Lighting |
   |---|---|---|
   | ⑦ 2026-10-29（VSync なし・2560×1369） | 16 | 0.442ms |
   | 2026-11-03 17:45（VSync なし・2560×1369） | 16 | 0.604ms |
   | 2026-11-17 22:09（VSync あり・2560×1440・F6 閉） | 30 | 1.071ms |
   上限を 16 → 30 にした分（+14 個 × 約 0.03ms ≒ +0.42ms）と、画素が 5% 増えた分で、ほぼ説明できる

 4. やること
================================================================================
 a. シェーダ（Pbr.hlsli）
    ・reaches(light, position)：平行光なら常に true。点・スポットは、位置までの距離の 2 乗 < 届く距離の 2 乗のときだけ true
    ・shadeSurface のループで、切り替えが入っていて reaches が false なら evaluateLight を呼ばずに次へ
    ・切り替えは gLightCount.y（> 0.5 で入）。ほかの切り替え（Ssr.hlsl の gSsrHiZ.z など）と同じ渡し方
    ・距離の 2 乗が届く距離の 2 乗以上なら、evaluateLight の窓はちょうど 0 なので、飛ばしても絵は 1 画素も変わらない

 b. C++（LightList::select）
    ・映る範囲（ViewFrustum。DrawCulling と同じ物）に、届く範囲の球を囲む箱が少しも入らないライトを一覧から外す
    ・平行光は外さない
    ・ディファードは映っている画素しか照らさない。半透明の板も映っている物しか描かない。SSR は映った色を映すだけ。
      なので、映る範囲に届かないライトは、どの画素の色にも足されていない。外しても絵は変わらない
    ・ViewFrustum は甘い側に倒す作り（映らない物を「映りうる」と答えることはあるが、逆は無い）なので、外しすぎない
    ・bind に描くカメラの射影×ビューと切り替えを渡す（SceneLights::setup が camera.projectionViewMatrix() と lightCullingEnabled() を渡す）

 c. 上限を揃える（Q3 の A）
    ・LightList.h の kMaxLights を 40 → 30

 切り替え：lightCullingEnabled()（LightingParams.h/.cpp。fogEnabled と同じ形。初期値 true。Release では true のまま）
           F6 → Render の Shadows・Instancing・PVS・LOD の並びに「Light culling」を足す

 回数の印（LightList::select）
    ・Light.candidates：足したライトの数
    ・Light.selected：シェーダへ送った数
    ・Light.culling：切り替えが入っている描画は 1（CSV で入/切のフレームを分けるため）

 5. 測り方
================================================================================
 ・Profile・VSync なし・夜・懐中電灯 ON・町の中心の交差点で、同じ向きのまま
 ・F7 で録りながら、F6 の Light culling を 入（約 40 秒）→ 切（約 40 秒）→ 入（約 40 秒）。録る間は F6 を閉じる
   （入を 2 回録るのは、時間とともに場面が変わった分を見分けるため。⑫で、録った順に GPU が少しずつ上がっていった反省）
 ・count.Light.culling でフレームを分け、切り替えの前後 1 秒は使わない
 ・比べる物：gpu.Lighting の中央値と 99% 点、GPU の合計、Light.selected、CPU（Scene.draw）
 ・絵が変わらないことは、入/切をその場で切り替えて目で見る。停電の日（F6 → Raid の Combo）でも同じことを見る

 6. どのくらい効くかの見込み（推定。測って直す）
================================================================================
 ・画素ごとに最後まで計算するライト：今は 30 個 → 月・懐中電灯・近くの街灯 2〜3 本の 4〜5 個
 ・飛ばすライトも、距離を比べる分の計算は残る
 ・gpu.Lighting：1.07ms → 0.3〜0.5ms 前後（−0.6ms 前後）
 ・CPU：映る範囲の判定がライト 55 個ぶん増えるだけ（ゾンビの判定と同じ箱の判定。0.01ms 程度の見込み）

================================================================================
 7. 懸念点
================================================================================
 ・GPU は画素を 32 個ずつまとめて同じ命令を進める。まとまりの中で届く画素と届かない画素が混ざると、両方の分の時間がかかる。
   それでも今（全部を計算）より遅くはならない。増えるのは距離を比べる 1 回分だけ
 ・映る範囲は、TAA でずらした行列から作る。ずれは 1 画素未満で、届く距離のふちでは光はほぼ 0 なので、絵には出ない
 ・F6 のライトの表示（LightDebugDrawer）では、画面の外のライトが「選ばれていない」色になる（正しい動き）
 ・観察用カメラの間は、そのカメラの映る範囲で選ぶ（SceneLights::setup が受け取るカメラが、描くカメラのため）
