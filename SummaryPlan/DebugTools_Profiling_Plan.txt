--------------------------------------------------------------------------------
 決定事項
--------------------------------------------------------------------------------
 ・計測結果には PC の性能情報も取得して書き出す（6-4 参照）
 ・性能の計測は「最適化した状態」で行う。

   ファイルは起動時に自動では読み込まない（5-3 参照）
 ・計測データは「ゲーム中に画面で見る」と「ファイルに書き出して後で見る」の両方を用意する

 ・Profile 構成の作り方

     おすすめ：計測の仕組みができてから、数字で効果を確かめながら行う

 1. 前提：今のコードで関係するところ
================================================================================

 項目            今の実装                                   影響すること
 --------------  -----------------------------------------  ----------------------------------
 メインループ    WindowCreator::update                      ImGui を差し込む場所がはっきりして
                 → Framework::preUpdate（beginDraw）        いる
                 → SceneManager::update
                   （ティック0～5回＋描画1回）
                 → Framework::postUpdate（Present）
 時間計測        WindowCreator().time()（ミリ秒の整数）と   精度が1msしかなく、フレーム予算の
                 60フレームの平均FPSだけ                    計測には使えない
 スワップチェーン BufferCount=1、DXGI_SWAP_EFFECT_DISCARD   VSync中はフレーム時間が常に16.6msに
                 Present( mVSync ? 1 : 0, 0 )              張り付き、余裕が見えない
 入力            GetKeyboardState / GetAsyncKeyState を     ImGui とマウス・キーボードを
                 毎フレーム読む。カーソルは ClipCursor と    取り合う（FPSで一番の問題）
                 ShowCursor でロック
 調整したい値    const float kWalkSpeed = 1.4f / ...        const なので起動中に変えられない。
                 のような定数が GameSrc に約137個            単位もティックあたり
 スキニング      GPU（SkinningPipeline が骨の行列を          ゾンビの負荷は CPU（アニメ・行列の
                 定数バッファで渡す）                        合成）と GPU（頂点処理）に分かれる
 ポストプロセス  PostProcess に中間の描画先がある           描画解像度を下げる実験が作りやすい
 デバイス作成    D3D11CreateDeviceAndSwapChain に            GPUが2つあるノートPCでは内蔵GPUが
                 アダプタ指定なし（nullptr）                選ばれることがある

 関係するファイル
  ・Framework.cpp                                    preUpdate / postUpdate、フレーム制限
  ・GameLib/src/Graphics/ManagerImpl.h                デバイス作成、beginDraw / endDraw（Present）
  ・GameLib/src/WindowCreator/WindowCreator.cpp       メッセージループ、WndProc
  ・GameLib/src/Input/ManagerImpl.h                   入力の読み取り、カーソルロック
  ・GameSrc/SceneManager.cpp、FixedStepClock.h        ティックの回し方
  ・GameSrc/GameTime.h                                1ティック＝1/60秒、上限5ティック

--------------------------------------------------------------------------------
 関係
--------------------------------------------------------------------------------
 フレーム時間 ≈ cpuWork + presentBlock + limiterSleep
 （limiterSleep は Framework::preUpdate の sleep(1) ループで待った時間）

 例                        cpuWork  presentBlock  フレーム時間  読み取れること
 ------------------------  -------  ------------  ------------  ----------------------
 A. VSync有効・軽い        4ms      12.6ms        16.67ms       CPU に余裕がある
 B. VSync有効・CPUが重い   15ms     1.6ms         16.67ms       ぎりぎり
 C. VSync無効・GPU律速     5ms      7ms           12ms          GPU を待っている
 D. VSync無効・CPU律速     11ms     0.1ms         11ms          CPU が限界

 A と B はフレーム時間が同じで見分けがつかない。分けて測る一番の理由はこれ。

 注意：endDraw() には Present のほかに capture()（スクリーンショット）も入っていて、
       これも GPU を待つ。正確に測るなら Present の呼び出しだけを囲む。

 3. ビルド構成（Profile 構成の新設）
================================================================================

 なぜ最適化した状態で測るのか
--------------------------------------------------------------------------------
 違い                    Debug                          Release
 ----------------------  -----------------------------  ----------------------------
 最適化                  なし（/Od）                    あり（/O2）
 STL のチェック          範囲チェックが毎回走る         なし
 ASSERT                  毎回チェックする               消える
 D3D11 デバッグレイヤー  有効（API呼び出しごとに検証）  無効

 Debug では処理によって3～10倍遅くなり、遅くなる割合も処理ごとにバラバラ。
 そのため Debug で測ると「アニメが一番重い」「CPU律速だ」のような間違った結論になりやすい。

--------------------------------------------------------------------------------
 構成の一覧
--------------------------------------------------------------------------------
 構成               最適化  エディタ・計測  用途
 -----------------  ------  --------------  ------------------------------------------
 Debug              なし    あり            不具合の調査（ステップ実行、ASSERT）
 Profile（新設）    あり    あり            性能の計測、値の調整、普段のプレイ確認
 Release            あり    なし            製品版

 Profile の中身（Release をコピーして2点だけ変える）
  ・プリプロセッサに ZF_EDITOR を追加する
  ・NDEBUG はそのまま（ASSERT と D3D デバッグレイヤーは無効）
  ・PDB の出力は今の Release で有効なのでそのまま（クラッシュ調査や外部ツール用）

--------------------------------------------------------------------------------
 作り方
--------------------------------------------------------------------------------
 方法：ファイルを直接編集する
  ・LastDrop.vcxproj に Profile|x64 を追加
  ・LastDrop.slnx に Profile を追加。
    SoundGen（音を作るツール）は Profile のとき Release を使うよう対応付ける
  ・出力先は x64\Profile\

--------------------------------------------------------------------------------
 使い分け
--------------------------------------------------------------------------------
 ・普段のプレイ確認・値の調整           → Profile（Debug でも可）
 ・性能の数字を見る・CSV を記録する     → 必ず Profile
 ・不具合をステップ実行で追う           → Debug
 ・D3D の使い方の誤りをチェックする     → Debug（ときどき）
 ・配布                                 → Release

 補足：ティック数が固定（1秒に60回）なので、Debug で描画が遅くてもゲームの進む速さは
       変わらない。ただし12fps 未満になると上限（5ティック/描画）に引っかかり、
       ゲーム自体が遅く進む。

 一緒に直す点：当たり判定の表示（F1）と、視線の先のゾンビを消す機能（F2）は
               今 #ifdef _DEBUG で囲まれているので Profile では使えない。
               条件を ZF_EDITOR に変更する。


================================================================================
 4. ImGui の導入
================================================================================

 置き場所
--------------------------------------------------------------------------------
 ・GameLib/src/ThirdParty/imgui/ に置く（miniaudio と同じ扱い。MITライセンス）
 ・バックエンドは imgui_impl_win32 と imgui_impl_dx11
 ・ウィンドウを本体から切り離す機能（docking）が要らなければ master 版で十分

--------------------------------------------------------------------------------
 差し込む場所（4か所）
--------------------------------------------------------------------------------
 1. WndProc（WindowCreator.cpp）
    先頭で ImGui_ImplWin32_WndProcHandler を呼ぶ。
    CharacterSet=MultiByte なので WM_CHAR は CP932 で届く。日本語入力を使うなら要確認。
 2. 初期化
    Graphics::Manager の mDevice / mContext は外から見えないので、
    GameLib/src/DebugUi/（DebugUi::create / begin / end）を作り、ManagerImpl に
    friend でアクセスさせる。GameLib が D3D11 を外に見せない設計を崩さずに済む。
 3. NewFrame：Framework::preUpdate の中、Input::Manager().update() の直後
 4. Render  ：Framework::postUpdate の中、mDebugStringRenderer.draw() の後、
              endDraw()（Present）の前
    ここに描いた物にはポストプロセスがかからない（UI にちょうどよい）。
    imgui_impl_dx11 は D3D のステートを保存して元に戻すので、GameLib が覚えている
    ステートとずれる心配もほぼない。

--------------------------------------------------------------------------------
 入力の取り合い（FPSならではの一番の問題）
--------------------------------------------------------------------------------
 ・エディタはキーで開閉する（F10 を提案）
 ・開いている間：カーソルロックを外し、視点を回さない。
   io.WantCaptureMouse / WantCaptureKeyboard が true なら Input::Manager::update で
   入力をゼロにする（ゲームは入力をポーリングしているので、まとめて止められるのはここだけ）
 ・閉じている間：io.ConfigFlags に NoMouse と NoMouseCursorChange を立て、
   ImGui が ShowCursor の参照カウントや WM_SETCURSOR を書き換えないようにする
 ・WantCapture* は NewFrame で決まるので、1フレーム前の値で判定する（通常の使い方）

--------------------------------------------------------------------------------
 一時停止とコマ送り
--------------------------------------------------------------------------------
 FixedStepClock に paused と timeScale を追加し、SceneManager::update で
 進めるティック数を調整する。drawWorld() は何回呼んでも同じ絵になる設計なので、
 一時停止中も描画を続けてよい。「1ティック進める」ボタンも付けられる。

--------------------------------------------------------------------------------
 日本語フォント（使う場合）
--------------------------------------------------------------------------------
 C:\Windows\Fonts\meiryo.ttc を GetGlyphRangesJapanese() で読み込む。
 ソースは /utf-8 でコンパイルしているので、表示文字列はそのまま UTF-8 で渡せる。


================================================================================
 5. エディタ機能（起動中の値の調整、ファイル保存）
================================================================================

--------------------------------------------------------------------------------
 5-1. 起動中に値を調整する仕組み
--------------------------------------------------------------------------------
 const float を、システムごとの「調整値の構造体」と visit 関数に置き換える。

   // 単位は「秒」で持つ。ティックあたりへの換算は使う側で行う。
   struct PlayerMoveParams{
       float walkSpeed    = 1.4f;  // m/s
       float runSpeed     = 3.2f;
       float acceleration = 8.f;   // m/s^2
       template< class V > void visit( V& v ){
           v( "walkSpeed",    walkSpeed,    0.f, 10.f, "m/s" );
           v( "runSpeed",     runSpeed,     0.f, 10.f, "m/s" );
           v( "acceleration", acceleration, 0.f, 50.f, "m/s^2" );
       }
   };

 ・同じ visit から「ImGui の描画」「ファイルへの保存」「読み込み」「既定値との比較」を作る。
   項目を足すときに直すのは1か所だけ。
 ・散らばった単発の値には TWEAK_FLOAT( "camera.bobAmount", 0.02f ) のような
   簡易的な登録制の仕組みも用意する。

 最初に移す候補（再ビルドの手間が大きい順）
  1. WeaponStance（銃の位置・角度）
  2. FirstPersonCamera（視野角・揺れ・感度）
  3. PlayerCharacter の速度と加速
  4. PostProcess のパラメータ
  5. 足音とフォーリーの音量・減衰

 注意
  ・ImGui での変更は描画フェーズ（ティックの間）に起きるので、シングルスレッドなら安全。
    ただし miniaudio のコールバックスレッドが読む値は、atomic にするか
    AudioEngine の API 経由で渡す。
  ・当たり判定の箱の大きさなど、placeObjects() で一度だけ登録される値は変えても
    すぐ反映されない。「要リスポーン」の印を付け、同じシーンを作り直すボタンを用意する。

--------------------------------------------------------------------------------
 5-2. 保存する「状態」は2種類に分ける
--------------------------------------------------------------------------------
 A. 調整値（データ）
    Params 構造体の値。プリセットとして Resource/Tuning/*.json などに保存する。
 B. ワールドの状態（スナップショット）
    自キャラの位置、カメラの yaw / pitch、ゾンビの一覧（位置・アニメの状態と時刻）、
    乱数のシード。Saves/*.json に保存する。
    「同じ視点・同じゾンビ数」で負荷を測れるので、ベンチマークの土台になる。

 ファイルの約束事
  ・ファイルにない項目は既定値を使う。知らない項目は警告を出して無視する
  ・バージョン番号を入れる
  ・保存は一時ファイルに書いてから MoveFileEx（REPLACE_EXISTING）で置き換える
  ・JSON ライブラリは nlohmann/json（ヘッダ1本）が手軽。
    GameLib の PseudoXml を使えば依存は増えないが、AI に書かせやすいのは JSON

--------------------------------------------------------------------------------
 5-3. コードの初期値を正とする場合の流れ（決定事項）
--------------------------------------------------------------------------------
 ファイルを起動時に自動で読み込むと、ファイルの値がコードより優先され
 「コードを直したのに反映されない」問題が起きる。そのため自動では読み込まない。

  1. ImGui で値を調整する（起動中だけ有効）
  2. 決まったら「C++ としてコピー」ボタンを押す。変更した値がコードの形で
     クリップボードに入るので、ソースに貼り付けて初期値を直す
       例： float walkSpeed = 1.55f;  // m/s
  3. 試している途中の値はプリセットとしてファイルに保存できる。
     読み込むのは「読み込み」ボタンを押したときだけ
  4. 既定値と違う項目は ImGui 上で色を変えて表示し、「既定値に戻す」ボタンを付ける

--------------------------------------------------------------------------------
 5-4. パネル構成の案
--------------------------------------------------------------------------------
 ・Scene   ：一時停止、コマ送り、時間の倍率、シーン切り替え、スナップショットの保存・読み込み
 ・Player / Camera / Weapon：調整値
 ・Zombies ：ActorList の一覧。選んだゾンビの当たり判定を CollisionDebugDrawer で表示、削除
 ・Audio   ：音量、減衰の確認
 ・Render  ：VSync、描画解像度の倍率、ポストプロセス、シェーダのエラー表示
 ・Perf    ：6章と7章の内容

 将来：建物や小物の配置を placeObjects のハードコードから level.json へ移し、
       ImGuizmo で動かせるようにする。


================================================================================
 6. フレーム予算と計測
================================================================================

 6-1. 考え方
--------------------------------------------------------------------------------
 ・ゲームの更新は1ティック（1/60秒）ごとに一定。描画は可変で、1回の描画で0～5ティック進む
 ・予算は描画の目標間隔で決める（60Hz：16.67ms、144Hz：6.94ms）
 ・重いフレームではティックが複数回走ってさらに重くなるので、
   ティックあたりの更新コストは予算の1/3程度に抑えるのが目安

--------------------------------------------------------------------------------
 6-2. 初期の予算案（60Hz 目標。計測して直していく前提の出発点）
--------------------------------------------------------------------------------
 CPU メインスレッド                            ms     GPU                    ms
 --------------------------------------------  -----  ---------------------  -----
 メッセージ処理・入力                          0.5    シーン（不透明物）     8.0
 更新（1ティック）：自キャラ・カメラ           0.5    スキンメッシュ         内訳を測る
 更新（1ティック）：ゾンビ（アニメ・行列合成）  2.0    ポストプロセス         1.0
 更新（1ティック）：当たり判定・命中判定       1.0    UI・ImGui              0.5
 描画コマンドの発行                            4.0
 音（メインスレッド側）                        0.5
 ImGui                                         0.5
 余裕                                          約7    余裕                   約7

--------------------------------------------------------------------------------
 6-3. 計測の仕組み
--------------------------------------------------------------------------------
 ・PROFILE_SCOPE( "Zombies.update" ) のようなスコープタイマー。
   QueryPerformanceCounter を使い、階層を持たせ、直近240フレームをリングバッファに残す。
   マクロにしておけば後から Tracy に差し替えられる
 ・フレームを cpuWork / presentBlock / limiterSleep に分けて測る（2章）
 ・計測のコスト：1区間あたり数十ナノ秒程度で、ほぼ影響しない

 今のコードで直す点
  ・時刻の取得を WindowCreator().time()（ミリ秒の整数）から QPC に変える
  ・setFrameRate の sleep(1) ループは VSync 有効なら不要。計測中は止める

--------------------------------------------------------------------------------
 6-4. 計測データの見方（画面とファイルの両方）
--------------------------------------------------------------------------------
 リングバッファに貯めたデータから、画面表示もファイル出力も作る（計測コードは1つ）。
 ファイルへ書くのはボタンを押したときやスパイクのときだけなので、ゲームは重くならない。

 段階                方法
 ------------------  ------------------------------------------------------------------
 普段の確認          画面に数字とグラフを常に出す
                     （ImGui 導入前は drawDebugString で数字だけ出す）
 スパイクの調査      予算を超えたフレームが出たら、その内訳を自動で JSON に保存
 変更前後の比較      ボタン（キー）で記録を開始・停止し、その間を CSV に書き出す
 定期的な性能チェック スナップショットを読み込み、決まったカメラの動きで N 秒走らせ、
                     平均・p95・p99・最大値を CSV に出す（ベンチマーク）

 画面表示の例
   frame 16.67ms  cpu 4.2ms  present 12.4ms  ticks 1

 CSV の例（1フレーム1行。Excel でそのままグラフにでき、AI も読みやすい）
   frame,frameMs,cpuWorkMs,presentMs,ticks,gpuMs
   1201,16.67,4.21,12.40,1,6.8
   1202,16.70,4.35,12.30,1,6.9

--------------------------------------------------------------------------------
 6-5. PC の性能情報の書き出し（決定事項）
--------------------------------------------------------------------------------
 CSV と同じ名前で、PC の情報を JSON にして並べて保存する
 （CSV の先頭に書くと Excel で開きにくくなるため）。
   例： perf_20261009_153000.csv と perf_20261009_153000_system.json

 項目                          取得方法
 ----------------------------  ------------------------------------------------
 CPU 名                        __cpuid のブランド文字列
 コア数・スレッド数            GetLogicalProcessorInformationEx
 メモリ容量                    GlobalMemoryStatusEx
 GPU 名・VRAM 容量             実際に使っている D3D11 デバイスの DXGI アダプタ情報
 GPU ドライバのバージョン      IDXGIAdapter::CheckInterfaceSupport
 OS のバージョン               RtlGetVersion
 解像度・リフレッシュレート    EnumDisplaySettings と実際のバックバッファの大きさ
 電源の状態（AC/バッテリー）   GetSystemPowerStatus
 計測条件                      ビルド構成、VSync の有無、目標フレームレート、日時

 「実際に使っている GPU」を記録すると、ノートPCで内蔵 GPU が選ばれている問題
 （1章のデバイス作成）にも気づける。


================================================================================
 7. CPU律速か GPU律速かの判定
================================================================================

 7-1. GPU 時間の測り方（D3D11）
--------------------------------------------------------------------------------
 ・D3D11_QUERY_TIMESTAMP_DISJOINT を1つと、D3D11_QUERY_TIMESTAMP をパスの数だけ用意し、
   フレーム開始・シーン・ポストプロセス・ImGui・フレーム終了で打つ
 ・結果は3～4フレーム前のものを読む（クエリのセットをリングで回す）。
   同じフレームで GetData を待つと CPU が GPU を待って止まり、計測が歪む
 ・Disjoint == TRUE のフレームは捨てる（クロックが変わって値が信用できない）

--------------------------------------------------------------------------------
 7-2. 判定のしかた
--------------------------------------------------------------------------------
 計測するときは VSync を切る（VSync 有効だと CPU も GPU も画面の更新待ちに見える）。
 F = フレーム間隔、C = cpuWork、G = GPU のフレーム時間、P = presentBlock

 状態                                  判定
 ------------------------------------  ------------------------------------------
 G ≈ F かつ C ≪ F で、P が大きい       GPU律速（CPU が Present で待たされている）
 C ≈ F かつ G ≪ F                      CPU律速（GPU が遊んでいる）
 両方が F に近い                       釣り合っている

 ・30フレームの平均に幅（ヒステリシス）を持たせ、
   「Bound: GPU (G=12.3 / C=5.1ms)」のように表示する
 ・Map(READ) や staging への読み戻し（capture()、Texture::lock）では CPU が GPU を待つ。
   こうした区間には印を付けて CPU の処理時間と区別する

--------------------------------------------------------------------------------
 7-3. 実験で確かめる（一番確実）
--------------------------------------------------------------------------------
 ・描画解像度を変える：PostProcess の中間の描画先を50%にする。
   速くなればピクセル処理で GPU律速。変わらなければ CPU律速か頂点処理が重い
 ・CPU に負荷を足す：更新処理に N ms の空回りを入れる。
   フレーム時間が変わらなければ CPU に余裕がある（GPU律速）
 ・ゾンビを2倍にする：CPU 側（アニメ・行列）と GPU 側（頂点処理）のどちらが伸びるか見る

--------------------------------------------------------------------------------
 7-4. スワップチェーンの見直し（後で別作業として）
--------------------------------------------------------------------------------
 FPS では入力の遅延も大事なので、次の変更を検討する。
  ・DXGI_SWAP_EFFECT_FLIP_DISCARD、BufferCount=2
  ・IDXGIDevice1::SetMaximumFrameLatency(1)、または待機可能なオブジェクト
  ・VSync を切るときのために DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING
 mAntiAlias（MSAA のバックバッファ）や capture() の作りと関わるので、
 計測の仕組みができてから数字で効果を確かめながら行う。
